# Spec — Local end-to-end integration (E)

Branch: `feat/ai-share-of-voice-app` (renamed from `local/e-integration`). Base: `feat/stats-results-tab`.
Goal: a working app that runs a real measurement end to end, without waiting for other teammates'
PRs. Nothing here is pushed; pieces that prove useful go upstream later as normal PRs by their owner.

## 1. Constraints

- `src/ai_share_of_voice/schemas/` stays unchanged. New code adapts to the contracts, not the other way.
- Every real component has a simulated twin (`LLM_MODE=simulated`), so `make check` never calls an API.
- Spending cap enforced in one place (the model client); CrewAI agents never get a raw key (see `agents/factory.py`).
- Analysis stays deterministic code (`stats/`, `tools/stats_tool.py`); the model only answers and writes text.
- `.env` is never read by tooling or committed; only `.env.example` documents variable names.

## 3. Requirements

R1. `llm_client.py`: `ModelClient` that returns `(schema_instance, schemas.llm.Usage)`, raises
`exceptions.BudgetExceeded`, logs every call, supports `simulated` and `live` modes, and separate
subject / agent / vision models.
R2. Real nodes (`nodes_real.py`): same signatures as `make_fake_nodes`, built from `NodeDeps` + client.
  - questions: load `data/questions_es.csv` or `questions.csv` by `Brief.language`.
  - sampling: ask the subject model each question once per batch; store raw answers in the run folder.
  - metrics: mention tool → `answers.csv` → stats tool → real `should_stop`.
  - research: real search (or fixture list in simulated mode), robots.txt, untrusted wrapping.
  - screenshots: vision on our own convergence/share chart (guaranteed path).
  - write_draft / skeptic: writer via model; skeptic node from `agents/skeptic.py`.
  - finalize: `automation/finalize.py`.
R3. `app.py` (Gradio): Brief tab → background run with event stream and spend bar → approval →
Results tab (`ui/results_tab.py`).
R4. `make check` green; new tests for R1 and R2 in simulated mode.
R5. One live run under 0.50 USD, logged in `runs/`.

### Product direction: any sector, not only the demo (added 2026-11-02)

Madrid food delivery is the demo. The product must serve a client of any sector and city
("where can I buy clothes in Valencia?"), and record every question with every business the
answer names, even when nobody told us to track it.

R6. Question panel for any sector.
  - Source, in order: an approved panel file (the demo CSVs, or one saved by a previous run of the
    same client) → otherwise generated by the agent model from sector, city and language.
  - Generated questions are checked in code: unique, 5–500 chars, and they never contain a tracked
    brand name or variant (a question that names the brand measures nothing). Rejected ones are
    regenerated once, then dropped.
  - Intents mixed: recommendation, where-to-buy, best-of / top-N, comparison, budget, nearby.
  - The panel is saved to `runs/<id>/questions.csv` and can be reused: the same panel across runs
    makes runs comparable (a change is due to the model, not to different questions).
R7. Discovery of every business named in an answer.
  - Per answer, the agent model lists every brand, store, app or website named (name, kind, URL if
    any). The answer is untrusted data, delimited in the prompt.
  - Code keeps only names that literally appear in the answer text (normalized like
    `normalize_brand_name`): a name the model invented is dropped. Names matching a tracked brand
    or variant are mapped to it.
  - Stored per batch in `runs/<id>/discovered/batch_NNN.jsonl` with `question_id`: question →
    businesses is recorded for every answer.
  - Report: untracked businesses ranked by mention rate (share of answers), with Wilson interval and
    number of questions; suggest adding as competitor above a threshold (proposed 10%, decision 7).
  - Local file format, no change to `schemas/`. Upstream later as decision 7 with J.
R9. The user can review the questions before the run (optional, added 2026-11-03).
  - "See the questions the AI will be asked" loads the panel (demo, or generated for the brief)
    in an editable table: the user can edit, delete or add questions. Skipping it runs as before.
  - The same code checks as for generated questions apply to the user's edits: 5–500 chars, no
    duplicates, never a tracked brand name or variant. Each problem is shown on its question; a
    panel with problems does not start. 3 to 30 questions.
  - The approved panel is saved as `runs/<id>/questions.csv` and asked in every batch, so the run
    is reproducible and can be repeated with the same questions.
R10. The user can read a real answer (added 2026-11-03).
  - Results show one real answer of the measured AI: a random question by default, or the one the
    user picks. Tracked brands are highlighted, the analysis of that answer is shown next to it
    (named / recommended per brand), and the text is escaped (it is untrusted model output).
  - Goal: the user sees where "named in 70%" comes from.
R11. Product review (2026-11-03), as a user and as a PM. Applied now, by impact:
  - Errors in plain words: a quota, budget or network failure says what happened and what to do;
    the technical text stays in the log.
  - Time before starting and progress by round ("round 2 of 3"): a live run takes minutes.
  - Results say which AI was measured and when: the figures are about one model on one date.
  - "What you can do now": rule-based actions from the figures (no model writing advice).
  - A short glossary in Results (named, recommended, margin of error, dated sample).
  - The draft is shown as formatted text, sanitized: no HTML, no images (tracking pixels).
  - "My measurements": past runs from `tracking.csv`, reopened from the SQLite checkpoints.
  Left for later: PDF export, alerts, more countries (the trend chart is R12).
R12. Trend over time in Results: the client's mention rate across past runs, each with its
  interval, only for runs with the same brand, sector, city and measured AI (a new model would
  look like a change of the brand), up to the run being viewed, last 12 at most. The last change
  is called clear only when the two intervals do not overlap (conservative); otherwise it may be
  chance. Shown only with two or more comparable runs.
  Every point is traceable to its question set: a fingerprint of the questions asked
  (`runs/<id>/questions.csv`, by text, without case, spaces or order), shown as a letter (A, B..)
  under each point, in a table with the questions of each set, and in `trend.csv` (model, set,
  set id, questions file). A change between different or unknown sets is never called clear.
R8. (Parked) Discovery-only run for a new client with no known competitors. Needs `Brief` to accept
  fewer than two competitors: schema change, so not in this branch.

## 5. Decisions

- D-a Provider: **Groq** (free tier, OpenAI-compatible). Decided 2026-11-02, updated 2026-11-03:
  Groq retired the Llama 3.3 and Llama 4 models, so the defaults in `config.py` are subject
  `openai/gpt-oss-20b` and agent `openai/gpt-oss-120b`. Groq has no vision model now: vision
  runs on Gemini (`VISION_PROVIDER=gemini`, `gemini-3.6-flash`). The Groq vision default in
  `config.py` still names the retired `llama-4-scout`; without `VISION_PROVIDER=gemini` the
  vision step fails and is skipped. Team decision 3 is still pending upstream.
- D-d Subject model while developing: **Groq `openai/gpt-oss-20b`** (free, high limits). Decided
  2026-11-02 after the Gemini free tier capped `gemini-3.6-flash` at 20 requests/day. Gemini stays
  for vision (few calls per run) and for the final measurement. Dev runs are functional checks,
  not measurements: the subject and the agents are the same model family.
- D-b Search backend: `none` (fixtures) by default; **Tavily** for live runs. Decided 2026-11-03
  after DuckDuckGo answered with a bot challenge (not bypassed).
- D-c Cap per run: 0.50 USD in `.env.example`. Proposed.
